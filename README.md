CRGO is an OWL 2 ontology for cybersecurity risk assessment. It gives a formal,
reasoner-checked meaning to the data that [CyberRiskGuardian](https://github.com/ITriskMgr/CyberRiskGuardian)
(CRG) produces: assets, threat and vulnerability descriptions, risk scenarios,
controls, the CRG quantitative parameters, the risk indices computed from them
and the key risk indicators used to monitor them. It replaces the earlier MOACCO ontology, which is retired; 0.11.0 adapted the parts of MOACCO that CRGO lacked (`docs/review-0.11.0.md`).

CRG's method follows the author's textbook: Léger, M.-A. (2026). *Introduction to Cybersecurity Governance for
Business Technology Management*, 3rd ed., v2.51 (October 2026), distributed with CyberRiskGuardian
(`plugins/crg-governance-textbook`). CRGO follows its wording: computed CRG values are *risk indices* (ch06),
key risk indicators are measured monitoring values (step 19), and AI or library values are marked
"Analytical estimate — validation required", missing facts "Information gap — organizational validation required"
and management choices "Management decision required".

- Upper ontology: BFO-2020 (ISO/IEC 21838-2), with an extract of the Common Core Ontologies 2.2 for information content entities, artifacts, agents and plans.
- Labels and definitions in English and French for every term.
- Governance annotations on every term: source, confidence, status, proposer, version.
- Licence: CC BY-NC 4.0 (see `LICENSE`); third-party imports keep their own licences (see `NOTICE.md`).

| crgo-iam | `https://w3id.org/crgo/crgo-iam` | 0.11.0: identities, accounts, roles, entitlements, segregation of duties, access reviews, privileged access, credentials (metadata only), emergency access, configuration items, baseline versions and deviations, change records, and the population-level registers of CyberRiskGuardian |

| crgo-full | `https://w3id.org/crgo/crgo-full` | crgo + scenario library (`data/abox/crgo-library.ttl`) + all vocabularies |

Import chains: `crg → measure → core → {gov, BFO-2020, CCO slice}`; `vuln → evidence → {measure, PROV-O slice, OWL-Time slice}`; `grc → {evidence, org}`; `org → core`; `mapping → gov`; `audit → assurance → governance → grc`; `incident → evidence`; `context → grc`; `iam → {soar, context}`. Term IRIs are
opaque (`https://w3id.org/crgo/CRGO_nnnnnnn`) and stay stable across versions;
the number assigned to each key is kept in `src/ids.tsv`.

The w3id.org identifiers resolve (registered 2026-10-11, perma-id/w3id.org#6858; 0.9.0 modules, work programmes and contract schemas added by #6862, merged 2026-10-11): browsers get the documentation,
RDF clients the Turtle files, and version IRIs the files at the release tag. For offline work, Protégé and ROBOT read
the local `ontology/catalog-v001.xml` automatically.

                 (CCM controls are built privately into ontology/vocab-private/, never committed)
pipeline/        library repair (pipeline/library), vocabulary builders (pipeline/vocab, incl. build_legal.py for legal instruments and source records), framework links (pipeline/links), CRG bridge (pipeline/crg), applicability evaluator (pipeline/grc)

shapes/          SHACL shapes (generated by src/build_shapes.py)

data/export/     crgo-identification.json (all scenarios with links, estimates and provenance)
data/library/    repaired 2023 scenario library: rows, families, category map, repair report
data/abox/       library instance data (crgo-library.ttl), proposed links awaiting review (crgo-library-proposed.ttl) and illustrative audit work programmes (crgo-workprogrammes.ttl); the proposal file is not imported by crgo-full
data/frameworks/ verified framework tables with their sources
contracts/       dss/v1: JSON Schemas of the CyberRiskGuardian data contract, examples, invalid cases (pipeline/contracts/dss.py); compliance/v1 and secops/v1: read contracts (pipeline/contracts/views.py)

The `.ttl` files in `ontology/` are generated. Edit the specification in `src/`
and rebuild rather than editing the Turtle by hand.

## Build and check

Requirements (0.11.1, documented after the test campaign of 8 November 2026):

- Python 3.10 or later with `rdflib`, `pyoxigraph` (query store, MCP server, identification tests), `pyshacl` (step 10, SHACL),
  `jsonschema` (contract tests) and `pandas` (library pipeline): `python3 -m pip install rdflib pyoxigraph pyshacl jsonschema pandas`.
  The MCP server and `tests/mcp/test_mcp_errors.py` also need `mcp>=1.2`.
- Java 11 or later (Java 21 works).
- [ROBOT](https://robot.obolibrary.org/) 1.9.6 or later, as a jar. Download `robot.jar` from the GitHub releases page
  (https://github.com/ontodev/robot/releases, asset `robot.jar`), not from Maven Central: sandboxes and CI runners that
  block Maven Central can still fetch GitHub release assets. Set `ROBOT_JAR` to the jar; `ROBOT_JAVA_ARGS` (default `-Xmx6g`)
  sizes the JVM. The 0.11.0 release was checked with ROBOT 1.9.11, the 0.11.1 campaign with 1.9.6.

```
ROBOT_JAR=/path/to/robot.jar ./scripts/check.sh                 # modules, fixtures, metadata, vocabularies, MediBec, samples, contracts (about 5 minutes)
ROBOT_JAR=/path/to/robot.jar WITH_LIBRARY=1 ./scripts/check.sh  # plus the full ontology with the library, SHACL, pitfalls, store, CQs and identification (about 35 minutes)
```

Timing (8 November 2026, 4 cores): the full run with `WITH_LIBRARY=1` takes about 35 minutes, most of it in step 9 (HermiT over
the full ontology, about 12 minutes) and step 10 (pySHACL over the library, about 19 minutes). Without the library it takes
about 5 minutes. Step 12 builds the Oxigraph store in `build/store/` (about 10 s); the MCP server reuses it.

Nothing tracked is rewritten by a check: step 1 regenerates the modules from `src/` (they must already be committed), step 10
writes the SHACL shapes to `build/crgo-shapes.ttl` and fails if they are not isomorphic to the tracked
`shapes/crgo-shapes.ttl` (after editing `src/build_shapes.py`, run `python3 src/build_shapes.py --write` and commit).

The script regenerates the modules and fixtures, merges the imports, then checks:

1. consistency and unsatisfiable classes with HermiT and ELK;
2. the OWL 2 DL profile, with imports;
3. the positive fixture is consistent and each negative fixture is inconsistent;
4. every term has en/fr labels and definitions, a status, a confidence and a source, and labels are unique per language;
5. no module refers to a term from a module it does not import.

Step 8 converts the MediBec case again when `CRG_CALC` points to CyberRiskGuardian's `crg_calc.py`;
`WITH_LIBRARY=1` adds steps 9 to 12 (full ontology with the scenario library, SHACL, pitfalls, store, competency questions, identification).

The Python suites alone (no ROBOT): `tests/cq/run_cq.py`, `tests/spec_cq/run_spec_cq.py`, `tests/grca_cq/run_grca_cq.py`,
`tests/pca_cq/run_pca_cq.py`, `tests/iam_cq/run_iam_cq.py`, `tests/identify/test_identify.py`, `tests/crg/check_roundtrip.py`,
`tests/contracts/test_dss_contract.py`, `tests/contracts/test_views_contract.py`, `tests/mcp/test_mcp_errors.py` (needs `mcp`),
`scripts/check_shacl.py` (needs `build/crgo-full-merged.ttl` from step 9). Build the store first: `python3 pipeline/query/store.py`.

To rebuild the Phase 3 data: `pipeline/fetch_sources.sh`, then `python3 pipeline/vocab/build_vocab.py`; for the library,
copy the 2023 `combined_file.xlsx` into `data/raw/` and run `pipeline/library/repair.py` then `build_abox.py`.

Large merges may need more memory: `JAVA_TOOL_OPTIONS=-Xmx8g`.

`python3 scripts/make_review_workbook.py` writes the term review workbook
(`build/CRGO-0.1.0-term-review.xlsx`, needs `openpyxl`) from `build/terms.json`.

## Profile

The core is OWL 2 DL and is kept inside OWL 2 EL where possible: no inverse
properties and no functional object properties (cardinality constraints will be
expressed in SHACL in Phase 4). The one known EL exception is the `xsd:boolean`
range of *is crown jewel*.
